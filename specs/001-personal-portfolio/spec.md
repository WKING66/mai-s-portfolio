## Clarifications

### Session 2026-09-25

- Q: 博客内容应采用哪一种创作与发布流程？ → A: 双入口：既可导入本地笔记，也可在站内新建和编辑，统一管理草稿、图片、标签及发布状态。
- Q: 网站最优先需要打动哪一类访客？ → A: 专业机会优先：招聘者与潜在合作方同等重要，同行和博客读者作为次要受众。
- Q: 访客浏览首页后，你最希望他们用哪一种气质来形容你？ → A: 冷静专业为主，现代科技点缀。
- Q: 三版静态页面应以哪种色彩与动效方向作为共同基线？ → A: 明暗双主题，默认跟随设备并使用一致的强调色；保留光效、视差和连续背景变化，同时为减少动态效果偏好提供完整静态替代。
- Q: 除首屏个人定位外，首页第二屏和主要视觉权重应优先展示什么内容？ → A: 用项目和博客呈现能力与成长；在校身份作为背景信息，首页优先展示作品、写作和具体贡献。

### Session 2026-09-25

- Q: 你准备上传的本地笔记主要是哪种格式？ → A: 笔记来源可能混用格式，但首版只导入 Markdown；导入模块保留接入 Word、PDF 等格式的扩展接口，站内仍只编辑 Markdown，文章至少可导出为 Markdown、Word（.docx）和 PDF。
- Q: 文章导出功能应开放给谁？ → A: 站点主人可导出自己的草稿和已发布文章；访客只能导出已发布且被站点主人明确允许下载的文章。
- Q: 首版导入 Markdown 笔记时，文中引用的本地图片需要自动一起导入吗？ → A: 需要；导入时同时接收被 Markdown 引用的本地图片，建立文章与图片的关联，缺失或失败时明确提示。阿里云 OSS 作为后续图片存储方案的候选，不在需求阶段定案。
- Q: 首版新增或修改项目作品，你希望在哪里操作？ → A: 在网站管理端新增、编辑和发布项目展示资料；只管理入口、介绍、标签、图片等展示内容，不上传项目源码或整个项目文件夹。
- Q: 首版每个项目需要网站内的独立详情页，还是展示卡片加外部入口就够了？ → A: 首版只需首页及项目列表的展示卡片，呈现图片、基本介绍、标签和本人贡献，并按需提供代码仓库或在线演示的外部入口；不做站内独立项目详情页。

### Session 2026-09-27（覆盖早期博客/数据库选择）

- PostgreSQL 替换 MySQL 为全站唯一关系型主库；MySQL 仅作为切换前开发预览。全部主键仍自增，状态与开关在 PostgreSQL 中用 SMALLINT。
- 统一 Document/DocumentVersion 为唯一正文来源；已发布文章再编辑时新版本先作为草稿，必须由站长显式重新发布。
- 首版只以 Markdown 导入、编辑、导出验收，Word/PDF 仅预留 Importer/Exporter 接口；覆盖上方早期“三格式导出”答复。
- 普通访客必须登录且账号有效，才可导出已发布并按篇允许下载的博客；匿名阅读不受影响。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 快速认识站点主人 (Priority: P1)

作为招聘者或潜在合作方，我希望进入网站后能迅速了解站点主人作为在校学生的真实身份、学习方向、核心能力和代表性成果，从而判断其潜力以及是否值得继续评估或建立联系。

**Why this priority**: 个人作品集首先要在很短时间内建立清晰、可信且有辨识度的个人印象。

**Independent Test**: 分别向招聘场景和潜在合作场景的测试者展示首页 10 秒后，询问其能否准确说出站点主人的定位、主要能力、至少一项代表成果以及下一步联系或深入了解的入口。

**Acceptance Scenarios**:

1. **Given** 访客首次打开首页，**When** 首屏完成呈现，**Then** 访客可以看到姓名或品牌名、职业定位、有内容的自我介绍、联系入口和前往代表作品的入口。
2. **Given** 访客希望进一步了解站点主人，**When** 浏览首屏后的内容，**Then** 能看到代表项目、博客文章以及由这些内容体现的能力，并能找到经过站点主人批准的联系方式或社交链接。
3. **Given** 访客使用手机或仅用键盘浏览，**When** 查看首页与主要导航，**Then** 核心信息与操作仍然完整、可读且可使用。
4. **Given** 站点主人已批准公开 GitHub 与邮箱、尚未提供简历文件，**When** 访客使用首页联系入口，**Then** GitHub 与邮箱能到达正确目标，Resume 明确显示待补充且不能下载空文件，未获批准的其他社交入口不出现。

### User Story 2 - 评估项目作品 (Priority: P1)

作为招聘者、潜在合作伙伴或同行，我希望通过项目卡片快速了解作品主题、站点主人的贡献、相关技术和可用的外部入口，以判断其真实能力与经验。

**Why this priority**: 项目作品是开发者作品集最重要的能力证据，与个人介绍共同构成首个可用版本。

**Independent Test**: 站点主人在管理端建立一项包含介绍、标签、图片及外部入口的项目展示资料并发布；测试者从首页或公开项目列表的卡片找到该项目、说明站点主人的贡献，并在入口存在时打开对应外部页面；未发布资料对访客不可见。

**Acceptance Scenarios**:

1. **Given** 站点存在多个项目，**When** 访客进入项目区域，**Then** 能通过标题、摘要、职责、标签和视觉预览快速区分项目。
2. **Given** 项目已发布，**When** 访客查看首页或项目列表中的展示卡片，**Then** 能看到图片、基本介绍、标签和站点主人的贡献；若站点主人提供了代码仓库或在线演示入口，访客可以从卡片打开对应外部页面，无需进入站内独立详情页。
3. **Given** 某项目没有演示、代码或图片，**When** 访客查看该项目，**Then** 页面不会出现失效占位或误导性入口，并仍能清楚说明项目价值。
4. **Given** 站点主人已进入项目管理页面，**When** 填写介绍、贡献、标签、图片和可选的代码或演示入口并保存，**Then** 资料作为未发布项目保留，可继续编辑，且无需上传项目源码或整个文件夹。
5. **Given** 站点主人明确发布或下架一个项目，**When** 访客浏览网站，**Then** 仅已发布的项目资料可见；下架后资料仍保留在管理端，访客不能通过旧入口继续访问。

### User Story 3 - 阅读本地笔记形成的博客 (Priority: P2)

作为对站点主人经验感兴趣的访客，我希望浏览由本地笔记导入或在站内创建、并经站点主人发布的文章，通过主题、摘要和阅读信息找到有价值的内容。

**Why this priority**: 博客展示持续学习、表达与知识沉淀能力，但在核心个人介绍和项目展示之后交付仍可保持网站价值。

**Independent Test**: 分别从本地笔记导入和站内新建一篇文章，使其进入同一套草稿、预览和发布流程，再验证访客只能找到并阅读已发布内容。

**Acceptance Scenarios**:

1. **Given** 已发布多篇文章，**When** 访客进入博客，**Then** 能看到标题、摘要、发布时间、主题和预计阅读时长，并能进入完整文章。
2. **Given** 文章包含代码、图片、引用或较长章节，**When** 访客阅读文章，**Then** 内容层级清楚、排版可读且不会超出阅读区域。
3. **Given** 本地笔记尚未达到公开标准，**When** 站点主人准备发布内容，**Then** 只有明确选择并完成必要整理的笔记会出现在公开网站上。

### User Story 4 - 在网站中直接撰写和管理博客 (Priority: P2)

作为站点主人，我希望首版能够导入 Markdown 笔记，并直接在网站中以 Markdown 创建、编辑、保存、发布和导出文章，同时管理图片与标签；后续可以扩展其他导入格式。

**Why this priority**: 单一 Markdown 内容源可让不同导入来源进入同一套编辑与发布流程；图片、标签及多格式导出满足持续维护和复用内容的需要，但整体优先级仍低于个人介绍与项目展示。

**Independent Test**: 导入一篇 Markdown 笔记，确认它成为可预览、可继续编辑的草稿；再在站内新建 Markdown 文章，保存、重新登录、发布，并分别导出 Markdown、Word（.docx）和 PDF。访客只能下载已发布且明确允许下载的文章；站点主人可导出自己的草稿与已发布文章。

**Acceptance Scenarios**:

1. **Given** 站点主人已进入博客管理页面，**When** 创建一篇新文章并填写标题、正文、摘要、主题等内容后保存，**Then** 文章内容会被持久化保存，并且重新进入网站后仍可继续编辑。
2. **Given** 站点主人正在编辑文章，**When** 使用 Markdown 编写标题、正文、列表、引用、链接、代码块等内容，**Then** 编辑器能够正确保存 Markdown 源文，并在文章预览和最终发布页面中正确呈现。
3. **Given** 站点主人使用 Markdown 编辑方式，**When** 输入符合 Markdown 语法的标题、列表、代码块、引用、链接或图片语法，**Then** 系统能够实时或通过预览模式正确渲染对应内容。
4. **Given** 站点主人重新打开已有文章，**When** 继续编辑正文，**Then** 编辑区仍是 Markdown 源文，不出现另一套富文本编辑格式或因往返转换丢失语义。
5. **Given** 站点主人正在编辑文章，**When** 上传 JPG、PNG、WebP 等支持的图片文件，**Then** 系统能够完成图片上传并将图片插入文章正文，同时保存图片与文章之间的引用关系。
6. **Given** 图片上传成功，**When** 站点主人预览或发布文章，**Then** 图片能够正常显示，并保持合理尺寸，不会超出正文阅读区域或破坏页面布局。
7. **Given** 图片格式不受支持、文件超过系统限制或上传失败，**When** 站点主人尝试上传图片，**Then** 系统应明确提示失败原因，并且不会产生无效或损坏的文章内容。
8. **Given** 站点主人正在编辑文章，**When** 为文章添加一个或多个标签，**Then** 标签信息会与文章一起保存，并在文章管理页面和公开文章页面中正确显示。
9. **Given** 系统中已经存在某个标签，**When** 站点主人再次为其他文章使用该标签，**Then** 系统应复用已有标签，而不是创建内容相同的重复标签。
10. **Given** 站点主人修改某篇文章的标签，**When** 添加或移除标签并保存，**Then** 文章与标签之间的关联应同步更新，并且不会影响其他文章已有的标签关联。
11. **Given** 已存在多个标签及对应文章，**When** 访客点击某个标签或通过标签筛选博客内容，**Then** 能够查看所有包含该标签的已发布文章。
12. **Given** 文章仍处于草稿状态，**When** 站点主人保存文章但未执行发布操作，**Then** 该文章不会出现在访客可访问的博客列表、标签页面或公开文章页面中。
13. **Given** 站点主人已经完成文章编辑，**When** 将文章状态设置为已发布，**Then** 文章会出现在公开博客列表中，并展示标题、摘要、发布时间、主题、标签和预计阅读时长，访客能够进入文章详情页完整阅读。
14. **Given** 一篇文章已经保存或发布，**When** 站点主人再次进入管理页面并修改文章内容，**Then** 可以更新正文、标题、摘要、主题、标签和图片等信息，并保存最新版本。
15. **Given** 文章正文包含代码、图片、引用、标题层级、列表或较长章节，**When** 站点主人在编辑过程中预览文章，**Then** 预览效果应与访客最终看到的文章展示效果基本一致，并保持清晰的内容层级和良好的可读性。
16. **Given** 站点主人正在撰写文章但尚未完成，**When** 主动保存草稿后离开编辑页面，**Then** 已输入的正文、格式、图片和标签信息不会丢失，并且之后能够继续编辑。
17. **Given** 站点主人不再希望公开某篇已发布文章，**When** 将文章重新设置为草稿、取消发布或执行下架操作，**Then** 该文章不再出现在公开博客列表、标签筛选结果和访客可访问的页面中，但文章内容、图片和标签信息仍保留在管理端。
18. **Given** 站点主人选择导入 Markdown（.md）笔记，**When** 导入完成，**Then** 系统生成可编辑的 Markdown 草稿并提供预览；不支持的格式或无效内容应明确提示，不得静默遗漏或自动发布。
19. **Given** 站点主人选择导出自己的草稿或已发布文章，**When** 选择 Markdown、Word（.docx）或 PDF，**Then** 系统生成对应文件，保留目标格式可表达的标题层级、正文、链接、代码与图片，且不改变文章发布状态。
20. **Given** 访客查看文章，**When** 文章已发布且站点主人明确允许下载，**Then** 访客可选择支持的格式导出该文章；若文章未发布或未允许下载，则访客看不到可用的导出入口，也不能通过直接请求取得文件。
21. **Given** 站点主人导入引用本地图片的 Markdown 笔记，**When** 同时提供所引用的图片文件，**Then** 图片随文章进入草稿，预览中正常显示，后续编辑和导出仍能使用；若引用的图片缺失或导入失败，系统应指出具体问题，不得把损坏的引用当作成功导入。
22. **Given** 站点主人导入引用网络图片的 Markdown 笔记，**When** 图片可安全取得且站点主人确认有权使用，**Then** 图片被归档为本站受控资源，正文不再依赖原始第三方地址；若无法取得或校验失败，导入保留为草稿并列出问题，不得自动发布。

### User Story 5 - 比较并确定设计方向 (Priority: P2)

作为站点主人，我希望先看到至少三种具有明显差异的静态页面概念，并比较它们的首屏、内容密度、色彩、字体、卡片、动效意向与移动端表现，从而选出最符合个人气质的组合。

**Why this priority**: 用户明确希望在确定模块和技术方案之前先通过可见原型讨论审美，减少后续因抽象描述产生的返工。

**Independent Test**: 展示三种使用相同示例内容的静态概念，验证站点主人能够指出偏好的整体方向及至少三个要保留或舍弃的具体元素。

**Acceptance Scenarios**:

1. **Given** 已完成参考信息收集，**When** 站点主人查看静态概念，**Then** 至少能比较三种在视觉语气和信息组织上明显不同、但内容范围一致的方向。
2. **Given** 站点主人在不同方案中偏好不同元素，**When** 提交反馈，**Then** 反馈可被记录为下一阶段的明确设计原则，而不要求立即决定技术栈。
3. **Given** 概念包含装饰或动效意向，**When** 访客偏好减少动态效果，**Then** 核心阅读与导航体验仍保持完整。
4. **Given** 访客查看任一设计概念，**When** 评价其整体印象，**Then** 首要感受应是冷静、专业和可信，科技感作为可辨识但不喧宾夺主的辅助特征。
5. **Given** 设备使用浅色或深色外观，**When** 打开任一设计概念，**Then** 页面应以对应主题呈现并保持一致的品牌强调色、清晰层级和足够对比度。
6. **Given** 页面包含光效、视差或连续背景变化，**When** 访客启用减少动态效果偏好，**Then** 连续或大幅运动停止，并以不丢失信息的静态效果替代。

### Edge Cases

- 当尚无项目或文章可公开时，页面应提供诚实、简洁的空状态，不能展示虚构成果。
- 当封面、截图或头像缺失时，页面应使用一致的文字型或图形型替代呈现，避免布局破损。
- 当项目名称、文章标题、代码片段或外部链接很长时，内容必须保持可读且不能造成横向溢出。
- 当外部演示、代码仓库或社交链接失效时，站点仍应保留项目说明，并避免让访客陷入无反馈的操作。
- 当项目尚未发布或被下架时，项目图片及其他展示资料不得通过公开列表或旧入口泄露；项目管理不接受源码仓库或整个项目文件夹作为上传内容。
- 当本地笔记包含私密信息、未授权图片或无法公开的引用时，这些内容不得因批量导入而自动公开。
- 当首版收到 Word、PDF 或无效 Markdown 文件时，导入必须给出明确的不支持或解析失败提示，不得生成看似成功的不完整草稿。
- 当 Markdown 引用的本地图片缺失、重名、格式不受支持或上传失败时，导入预览必须指出受影响的引用，不能静默丢失图片或自动发布。
- 当网络图片地址指向站点内部或私有网络、发生不安全跳转、内容过大、实际格式不符或来源拒绝下载时，系统必须拒绝获取并报告受影响的引用，不得直接保留第三方地址作为公开图片。
- 当文章从已发布改为草稿或关闭下载许可时，访客已有页面上的导出入口应失效，直接下载请求也必须被拒绝。
- 当设备、浏览器或网络能力有限时，核心介绍、项目和文章文字仍应优先可访问；非核心视觉效果可以降级。
- 当用户选择减少动态效果、放大文字或仅使用键盘时，所有主要内容与操作仍应可访问。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 网站 MUST 提供清晰的全局导航，使访客能够到达个人介绍、项目、博客以及经批准的联系入口。
- **FR-002**: 首页 MUST 在首个主要可视区域呈现站点主人的姓名或品牌名、职业定位、有内容的自我介绍、联系入口和前往代表作品的入口。
- **FR-003**: 网站 MUST 提供独立且易找到的自我介绍区域，说明兴趣方向、做事方式和正在关注的问题，并支持呈现教育、课程、证书或其他由站点主人选择公开的可信信息。
- **FR-004**: 网站 MUST 提供项目集合；每个项目至少包含标题、摘要、站点主人的角色或贡献、相关能力标签和可用状态。
- **FR-005**: 首版 MUST 在首页或项目列表以展示卡片呈现重点项目的图片、基本介绍、能力标签和站点主人的具体贡献，并按实际情况提供经确认的外部代码或演示入口；不要求站内独立项目详情页。
- **FR-006**: 网站 MUST 提供博客文章列表与文章阅读页面；文章至少包含标题、摘要、正文、发布时间和主题信息。
- **FR-007**: 站点主人 MUST 能从本地笔记中明确选择要公开的内容；未选择、未完成或标记为私密的内容不得公开。
- **FR-008**: 博客 MUST 正确呈现常见的技术写作内容，包括分级标题、列表、引用、链接、图片和代码示例。
- **FR-009**: 网站 MUST 在桌面、平板与手机尺寸下保持完整的信息层级、可读性与可操作性。
- **FR-010**: 所有主要导航与交互 MUST 可通过键盘完成，并在合理的文字缩放和减少动态效果偏好下保持可用。
- **FR-011**: 网站 MUST 对缺少媒体、空项目集合、空文章集合和失效外部链接提供清楚且不误导的替代状态。
- **FR-012**: 网站 MUST 只公开站点主人明确批准的个人资料、联系方式、简历文件和外部账号；已批准但尚未提供文件的简历入口必须显示待补充且不可下载。
- **FR-013**: 在最终视觉方案确定前，设计探索 MUST 提供至少三种使用同一组示例内容的静态页面概念，以便公平比较信息组织与视觉表达。
- **FR-014**: 每个静态概念 MUST 至少展示首页首屏、个人介绍、项目卡片、文章入口以及桌面与手机布局意向。
- **FR-015**: 设计讨论结果 MUST 记录站点主人选择的整体方向、需要保留的元素、需要避免的元素以及仍待验证的体验假设。
- **FR-016**: 视觉体验 SHOULD 借鉴用户所选参考站点的现代开发者作品集特征，例如明确的分区、强层级、项目与能力证据，但 MUST 保持站点主人自己的身份表达，不能直接复制参考作品。
- **FR-017**: 首版博客管理 MUST 支持导入站点主人明确选择的 Markdown（.md）笔记并生成统一 Document 的草稿版本；站内新建也保存为 Markdown 版本。已发布内容再次编辑后，访客仍读取旧发布版本，只有站长显式重新发布才切换公开版本。
- **FR-018**: 文章管理、图片上传、标签维护和发布状态变更 MUST 仅对经过验证的站点主人开放；访客只能访问已发布内容。
- **FR-019**: 系统 MUST 在导入任务中记录文档导入来源，并在 BlogPost 中记录当前发布状态；来源差异不得产生第二套正文，也不得影响后续编辑、预览、标签管理或公开阅读体验。
- **FR-020**: 首页的信息层级 MUST 同等支持招聘评估与合作评估，使两类访客都能快速查看代表项目、理解站点主人的具体贡献并找到联系入口；面向同行和博客读者的内容作为次级入口呈现。
- **FR-021**: 设计概念 MUST 以冷静、专业、可信和有序为主要气质，并通过克制的字体细节、线条、状态反馈或装饰体现现代科技感；科技元素不得降低内容可读性或项目证据的优先级。
- **FR-022**: 每个设计概念 MUST 提供协调的浅色与深色主题，默认跟随访客设备外观，并在两种主题中保持一致的品牌强调色、内容层级和可读性。
- **FR-023**: 设计概念 MAY 使用光效、视差和连续背景变化增强科技感，但 MUST 提供完整的减少动态效果版本；动效不得阻碍阅读、操作、首屏识别或页面性能目标。
- **FR-024**: 首页首屏后沿用已选 A 版先展示技术栈，再呈现代表项目和博客文章；项目/博客仍须以具体贡献、成果和思考过程承担主要能力证据，教育、课程或证书仅作补充，不因技术栈先出现而淹没作品内容。
- **FR-025**: 网站 MUST 以站点主人的学习方向、核心能力、项目、博客、课程或证书和可验证成果建立正面专业形象；不得主动强调履历空缺，也不得使用未经证实的职位、组织或成果。
- **FR-026**: 首页 MUST 提供技术栈展示，按清楚的类别组织站点主人实际使用的语言、框架或工具、基础设施和数据技术；每项技术可关联体现其使用的项目，尚未确认的技术不得作为真实能力发布。
- **FR-027**: 首页 MUST 同时提供首屏联系入口和完整联系区域；在联系方式尚未提供时，静态原型应清楚标注为待替换示例，避免把占位地址当作真实联系方式。
- **FR-028**: 三版视觉原型中至少一版 MUST 明确借鉴 Wilson Costa 参考站可观察的页面语言：固定导航、姓名与简介作为开场、深色蓝调光晕、半透明分组卡片、技术分类、项目、学习成果或证书，以及联系区；其余版本可探索不同表达。
- **FR-029**: 所选 A 版视觉原型 MUST 将已获批准的简历、GitHub 和邮箱快捷入口直接放在首屏自我介绍下方，以圆角按钮呈现；简历文件暂缺时入口不可下载，未获批准的 LinkedIn 不显示。
- **FR-030**: A 版卡片 MUST 呈现缓慢流动的表面光、指针跟随的柔和光斑和小幅倾斜反馈；触控或减少动态效果环境 MUST 保持稳定、可读的静态卡片，不依赖动效传达信息。
- **FR-031**: A 版技术栈 MUST 参考所选网站采用分组大卡片与技术 Logo 展示，每组 Logo 有连续横向移动效果，单个 Logo 不使用独立边框或底色；技术名称仍可读，减少动态效果时停止移动，未获站点主人确认的示例技术必须明确标注为待确认。
- **FR-032**: 博客管理 MUST 仅以 Markdown 作为文章正文的编辑与保存格式；公开阅读页按 Markdown 语义渲染，不提供独立的富文本编辑模式。
- **FR-033**: 首版站点主人 MUST 能将自己的草稿和已发布 DocumentVersion 导出为 Markdown（.md），保留正文结构、代码、链接和已归档图片引用，且不得改变发布状态；Word（.docx）和 PDF 导出只预留 Exporter 扩展接口，第二阶段再实现和验收。
- **FR-034**: Markdown 导入 MUST 提供预览和解析问题提示；不支持的文件或无法可靠保留的内容不得静默接受，导入结果不得自动发布。
- **FR-035**: 导入模块 MUST 保留可扩展的格式接入接口，使后续添加 Word、PDF 等输入格式时仍沿用同一 Markdown 草稿、预览和发布流程；首版不要求实际导入这些格式。
- **FR-036**: 普通访客 MUST 登录且账号有效，才能以站点当前支持的格式导出已发布且站点主人按篇明确允许下载的版本；默认不允许下载，撤销许可或下架后直接请求必须失效。站点主人对自己草稿和已发布版本的导出不受访客许可限制；公开阅读仍可匿名。
- **FR-037**: 首版 Markdown 导入 MUST 能同时接收正文引用的本地图片、建立图片与文章的关联，并在草稿预览、发布页和导出结果中保持可用；缺失、冲突或失败的图片引用必须有明确提示，导入结果不得自动发布。
- **FR-038**: 首版 MUST 仅向经过验证的站点主人提供项目展示资料的站内新增、编辑、保存、发布与下架能力；项目资料包含基本介绍、本人贡献、标签、展示图片和可选的代码或演示入口，不要求也不提供整个项目文件夹或源码上传。访客只能访问已发布的项目资料。
- **FR-039**: 个人资料区 MUST 在尚无头像时呈现明确的非真人占位状态，并为后续由站点主人上传或更换头像保留入口；不得使用未经提供或批准的人像冒充本人。
- **FR-040**: 公开页面 MUST 让搜索服务及可读取页面的 AI 系统直接获取有意义的标题、描述、正文、作者、日期和稳定内容地址；文章与项目应提供适当的可机器识别元数据，避免仅在访客执行脚本后才出现核心内容。
- **FR-041**: 站点主人导入或插入的本地图片与网络图片 MUST 经过统一的受控归档流程后再用于文章或项目展示；网络图片不得在正式内容中长期依赖第三方原始地址。归档失败须指出具体图片并阻止自动发布。
- **FR-042**: 首版内容模型 MUST 保留项目、Document、BlogPost 的稳定标识及版本化公开状态；第二版面向访客的 Agent 每次检索只可引用当前已发布版本或独立批准公开的知识版本，不得因草稿已建立索引而泄露内容。首版不要求 Agent 问答功能。
- **FR-043**: 后端 MUST 提供与实际接口一致的 OpenAPI 规范和 Swagger 可视化接口文档，覆盖公开与管理接口的请求、响应、认证和主要错误；本地开发时可访问，正式环境不得无保护地暴露管理接口的交互式调试入口。
- **FR-044**: 所有业务输入、唯一性、关联目标、状态转换和权限 MUST 在后端服务层先校验并返回明确错误，不得依赖 PostgreSQL 异常完成正常校验。数据库 MAY 建唯一索引和物理外键维护完整性；外键不得使用级联删除，关联清理由服务层在事务中显式完成。
- **FR-045**: 账号模型 MUST 区分站点主人与普通访客两种类型；普通访客类型不得取得管理权限。公开作品集阅读不要求登录，但博客访客导出上线前 MUST 提供普通账号注册/登录及有效状态校验；首版不要求个人中心。
- **FR-046**: PostgreSQL 所有表 MUST 使用自增 BIGINT 主键，包括媒体表与关联表；PostgreSQL 不提供 TINYINT，状态、类别、角色及 0/1 开关统一用 SMALLINT 数值编码，不使用 Boolean 或 VARCHAR 保存枚举状态。主键可预测不得影响逐次权限校验。
- **FR-047**: DocumentVersion MUST 是不可变内容快照；版本化标题、摘要、Markdown、阅读时长、标签显示信息及 Asset 清单均不得因草稿编辑或全局标签/媒体变更而悄悄改变已发布内容。
- **FR-048**: 服务层 MUST 校验 Markdown 中每个 `asset://` 引用属于该版本的已授权 READY Asset；公开解析、媒体读取和导出每次均按当前发布版本及用途校验权限，不能仅凭媒体 ID 放行。READY Asset 的存储对象不得原地覆盖。
- **FR-049**: 从 MySQL 切到 PostgreSQL 前 MUST 可恢复备份、暂停写入、确定性迁移旧数据并核对账号密码哈希、文章到 Document/Blog/Version 的映射、关联数量与自增序列；迁移验证失败时保持现有预览库不变。

### Scope Boundaries

- 本功能包含个人形象展示、项目作品、由本地笔记导入或在站内创建并统一管理的博客，以及实施前的多方案静态设计探索。
- 前后端分离、服务端呈现公开内容、关系型数据与对象存储等实现选择在同目录 `plan.md` 中确定；服务器、域名和正式部署流水线在本地首版跑通后再决定。
- 首个版本的作品集展示可匿名浏览；普通访客注册/登录只作为博客导出的前置能力，在博客模块阶段实现，不扩展评论系统、付费内容、邮件订阅、实时聊天、社交网络或个人中心。
- 首个版本不要求自动监控整个本地笔记目录或把所有笔记同步到公开网站；本地笔记必须由站点主人主动选择并导入统一的文章管理流程。
- 首个版本只要求 Markdown 笔记导入；Word、PDF 等格式导入留待后续迭代，但导入格式扩展接口在首版预留。
- 项目管理仅面向作品展示资料和图片，不承载项目源码、依赖或整个项目目录；代码与在线演示通过经站点主人确认的外部入口连接。
- 首版项目使用首页及项目列表的展示卡片，不包含站内独立项目详情页。
- 第二版可增加让访客通过 AI Agent 了解站点主人及公开项目的功能；首版不接入模型、不构建向量检索，也不因后续设想强行增加缓存系统。
- 在真实项目与文章资料尚未提供时，演示项目和 Markdown 测试笔记只用于布局及功能验证，不得被正式公开站点当作站点主人的真实作品发布。
- 数据分析、搜索、标签筛选、完整双语支持和可下载简历可以在后续澄清中决定是否纳入首个版本。

### Key Entities *(include if feature involves data)*

- **个人资料**: 代表站点主人公开身份，包括姓名或品牌名、职业定位、简介、能力、经历、成就、可为空的头像或代表图以及经批准的联系渠道；未提供的简历文件不产生下载目标。
- **项目**: 代表一个作品的展示资料，包括标题、摘要、说明、站点主人角色或贡献、能力标签、时间信息、展示图片、成果、可选的演示或代码入口，以及草稿或已发布状态；不包含项目源码或完整项目文件夹。
- **Document / DocumentVersion**: Document 是内容身份；不可变 Version 保存 Markdown、标题、摘要、阅读时长、标签显示快照和 Asset 清单。导入来源留在导入任务中，不另建文章正文。
- **BlogPost**: Document 的博客发布视图，保存 slug、状态、当前已发布版本指针和默认关闭的访客下载许可；站长保存新草稿不会直接改变公开内容。
- **图片资源**: 代表文章正文、封面或项目展示引用的图片，包括本地或网络来源、受控归档状态、所属内容关联和公开状态；导入时由站点主人明确提供或引用，未发布内容的图片不得仅因导入而公开成为可发现的内容。
- **主题**: 用于描述项目能力领域或文章内容领域，支持访客理解内容关联；一个项目或文章可关联多个主题。
- **设计概念**: 代表一套可比较的静态视觉方向，包括视觉语气、色彩、字体层级、布局、内容密度、动效意向和响应式示例。
- **外部链接**: 代表演示、代码仓库、社交账号、证书或联系方式，包含用途、目标地址、公开状态和可用状态。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在招聘场景和潜在合作场景中，各至少 80% 的首次测试访客在查看首页 10 秒后，能正确说出站点主人的职业定位、至少一项核心能力以及继续评估或联系的入口。
- **SC-002**: 至少 90% 的测试访客能在不超过两次选择操作内，从首页找到任一重点项目的展示卡片及其可用的外部入口。
- **SC-003**: 至少 90% 的测试访客能在不超过三次选择操作内找到并打开指定主题的博客文章。
- **SC-004**: 在 360、768 和 1440 像素宽度的代表性视口中，核心页面不存在遮挡、内容截断或必须横向滚动才能阅读的情况。
- **SC-005**: 在普通移动网络条件下，至少 90% 的测试访问能在 3 秒内看到可阅读的首屏身份信息；非核心视觉效果不得阻碍阅读。
- **SC-006**: 所有主要浏览任务都可仅使用键盘完成，且减少动态效果后不丢失任何核心信息或操作。
- **SC-007**: 站点主人能够把一篇已完成且符合公开条件的本地笔记整理成可发布文章，人工内容准备时间不超过 5 分钟。
- **SC-008**: 设计评审时，三种静态概念在视觉语气与信息组织上可被站点主人明确区分，并能形成至少三条具体、可执行的偏好结论。
- **SC-009**: 在包含缺失图片、无外部演示和超长标题的测试内容下，100% 的项目与文章页面仍保持可读并提供明确状态说明。
- **SC-010**: 在设计概念评价中，至少 80% 的目标受众将整体首先描述为冷静、专业或可信，同时至少 60% 能识别出克制的现代科技特征。
- **SC-011**: 三种设计概念在浅色与深色外观下均通过核心阅读与操作测试；启用减少动态效果后，100% 的核心信息和操作仍然可用，且不存在持续位移或视差运动。
- **SC-012**: 至少 80% 的目标受众在浏览首页前两屏后，能说出至少一个项目或一篇文章，以及它体现的能力或思考；页面不以履历空缺作为卖点。
- **SC-013**: 在 360 和 1440 像素宽度下，测试访客均能从首页首屏找到联系入口，并能在一次导航操作内到达自我介绍、技术栈、项目、博客和联系区域。
- **SC-014**: 至少一篇 Markdown 样本导入后能预览并继续编辑；含标题、代码、链接和图片的版本导出的 Markdown 文件可打开且状态不变；未登录、未发布或未允许下载时普通访客无法取得导出文件。Word/PDF 不计入首版验收。
- **SC-015**: 一篇引用至少两张本地图片的 Markdown 样本导入后，两张图片均能在草稿预览和文章导出中正常显示；移除其中一张输入图片后，导入流程能准确指出缺失引用，且不会自动发布文章。
- **SC-016**: 站点主人能在管理端新增并编辑一项含介绍、标签和图片的项目展示资料，保存后访客不可见，明确发布后可见，下架后访客无法继续访问；全流程无需上传项目源码或完整目录。
- **SC-017**: 使用已确认的首页入口配置测试时，GitHub 与邮箱均能打开正确目标，Resume 无文件时不能下载，未获批准的社交账号不显示；未提供头像时不出现虚构人像。
- **SC-018**: 首页、项目列表和已发布文章的初始页面响应包含可读正文及各自的标题、描述和规范地址；站点地图只列出已发布内容，下架内容不再出现在公开元数据中。
- **SC-019**: 同一篇测试笔记中的同目录图片、多级目录图片和网络图片导入后均关联到受控图片资源；任一图片归档失败时列出对应引用，草稿保持未发布，正式内容不继续引用第三方原始图片地址。
- **SC-020**: 本地启动后可打开 Swagger 接口页并取得 OpenAPI JSON；其中公开与管理接口的路径、输入、输出、登录要求和关键错误与实测行为一致，生产配置下未授权访客不能使用管理接口调试页。
- **SC-021**: 非法关联 ID、重复 slug/关系、非法状态值均由服务端给出明确业务错误，不向用户暴露 SQL 异常；数据库唯一索引和外键存在但不承担正常输入校验，内容下架与显式清理后不产生孤儿关联。
- **SC-022**: 账号表同时支持站点主人和普通访客类型；普通访客可注册/登录并在文章允许时导出，使用普通访客账号请求管理接口被拒绝，匿名阅读仍无需创建账号。
- **SC-023**: 首版 PostgreSQL 每张表的唯一主键均为自增 `id`；数据库中所有状态、类别、角色和 0/1 开关均为 SMALLINT 编码；重复关联先由服务端给出明确错误，组合唯一索引维持数据完整性；枚举媒体 ID 无法读取未公开图片。
- **SC-024**: 发布 v1 后保存 v2，匿名页面及公开 Asset 仍只呈现 v1；显式重新发布才呈现 v2 的标题、摘要、阅读时长、标签、封面和正文；修改全局标签或替换媒体对象也不能改变 v1 的快照。
- **SC-025**: PostgreSQL 迁移通过真实数据库结构与数据比对；未通过时不切换运行配置。
- **SC-026**: 第二阶段公开 Agent 的检索测试无法读到任一未发布版本，即使该版本已有索引；撤稿后也不能继续引用旧索引内容。

## Assumptions

- 首要受众为招聘者与潜在合作方，两者同等重要；同行和博客读者为次要受众。所有访客默认无需登录即可阅读公开内容。
- 站点主人是在校学生；内容叙事以潜力、学习方向、核心能力、个人项目、博客、课程或证书和持续输出建立可信度，不主动讨论履历空缺。
- 初始版本由站点主人单独维护，不包含多人协作、审批流或访客创建内容的能力。
- 本地 Markdown 笔记需要经过人工选择、清理隐私信息和补充公开元数据后导入统一文章管理流程；导入不会自动公开内容，站内新建文章也必须经过明确发布才能被访客看到。Word/PDF 导入为后续扩展，不属于首版。
- 初始版本使用一种主要展示语言；完整的多语言切换不作为默认范围，但内容中可以保留必要的中英文术语。
- 参考的开发者作品集合集用于拓宽版式与内容灵感；Wilson Costa 作品集提供固定导航、个人介绍、技术分类、项目、证书与联系区，以及深色蓝调、光晕和半透明卡片的视觉参考，不要求逐像素复制。
- 个人气质以冷静专业为主，现代科技感只作为视觉与交互点缀，不采用喧闹、游戏化或过度实验性的整体表达。
- 视觉方案支持浅色与深色两套协调外观并默认跟随设备；光效、视差和连续背景变化可以作为科技感表达，但必须可被系统的减少动态效果偏好安全降级。
- 在获得真实个人资料、项目与文章内容前，静态概念可以使用清楚标记的示例内容；正式网站不得把示例内容当作真实履历发布。
- 站点主人已确认的公开文案、入口和技术展示清单单独记录于 `content/confirmed-content.md`；真实项目、简历文件和可公开博客笔记尚未提供，仓库中的示例仅作测试。
- 具体模块拆分、技术栈和内容来源接入方式由同目录 `plan.md` 规划；服务器、域名与正式部署方案待本地首版跑通后再确定。
- 站点以中国内地访客为主要服务对象。已确定的具体框架、数据库和图片存储约束及第二版 Agent 的边界见同目录 `plan.md`；服务器与域名待首版本地运行后选择。
