# PostgreSQL 与统一 Document 重构：首个审核点

状态：2026-09-27 已在独立 PostgreSQL `portfolio_dev` 实测基线并将本地 `dev` 后端切换至 PostgreSQL；Document/Blog 业务实现仍待后续模块审核。

## 已确认边界

- PostgreSQL 替换 MySQL，成为整个项目唯一关系型主库。Redis 仍不保存唯一业务真源；二进制 Asset 最终由阿里云 OSS 保存。
- 首版以 Markdown 导入与编辑验证统一 Document 链路；Word/PDF 的格式差异只能留在 Importer/Exporter 边界，本次不编写假实现或宣称已支持。
- 已发布博客再次编辑产生新的 DocumentVersion；公开页面仍使用 `blog_post.published_version_id`，只有站长显式重新发布才切换该指针。
- 继续使用用户确认的三层架构：Controller → Service 接口及实现 → Mapper。文档、博客、知识、存储按职责划分，不新增一套相互独立的博客正文。
- 账号、资料、项目与标签的现有 API 路径、鉴权和响应行为在数据库切换时保持不变。

## 持久化真源与表映射

| 现有 MySQL | PostgreSQL 目标 | 说明 |
| --- | --- | --- |
| `user_account`, `site_config`, `tag` | 同名表 | 保留站长密码哈希、资料与标签；不重新初始化覆盖已有值。 |
| `project`, `project_link`, `project_tag`, `project_media` | 同名表 | 保留现有项目展示模型。 |
| `media_asset` | 同名表 | 只保存 Asset 元数据；二进制对象由 ObjectStorage 管理。 |
| `article.body_markdown` | `document` + `document_version.markdown_content` | 文档版本是唯一正文真源；`document.origin_type` 仅记录站内创建/导入来源，不据此拆分正文模型。 |
| `article` 的发布字段 | `blog_post` | 博客只保存公开 slug、权限、发布状态和已发布版本指针。标题、摘要、阅读时长放在文档版本中，封面是该版本的 Asset；编辑它们也须重新发布才对访客可见。 |
| `article_media`, `article_tag` | `document_version_asset`, `document_version_tag` | 资源与标签跟随版本；标签显示名称和 slug 在关联行中留快照，避免修改全局 Tag 时悄悄改变旧版本。 |
| `article_import_job` | `document_import_job` | 导入格式和问题留在边界，不污染 Document 正文模型。 |
| 无 | `document_processing_task` | 为异步任务、重试和定时恢复保留持久状态。 |

PostgreSQL 使用 `BIGINT GENERATED BY DEFAULT AS IDENTITY` 实现全部自增主键，便于迁移时保留旧 ID；PostgreSQL 没有原生 `TINYINT`，状态/类别/开关改为数值型 `SMALLINT`，Java 侧继续用枚举校验，不改用布尔或字符串。时间列保持无时区时间戳并由应用统一写 UTC；`BINARY(32)` 对应 `BYTEA`，JSON 对应 `JSONB`。唯一索引与 `ON DELETE RESTRICT` 物理外键保留，但业务校验仍先在服务端执行，不新增业务 `CHECK` 约束。

迁移脚本通过 `COMMENT ON TABLE` 和 `COMMENT ON COLUMN` 为每张表、每个字段提供数据库级 description（用途、单位、空值及已确定的数值码）。这些注释是审阅和元数据说明，不替代 Service 枚举校验。`document_import_job.status` 与 `document_processing_task.status` 的生命周期语义已经列明，具体数字码尚未定稿，不在数据库注释中虚构；投入使用前必须同步 Java 枚举、接口合同与测试。旧 MySQL `article_import_job.status` 的 0=失败、1=完成，迁移时必须按新枚举显式转换，不能直接复制数值。

MySQL 现有开发库使用不区分大小写的排序规则；PostgreSQL 默认比较语义不同。用户名及对外 slug 使用 `LOWER(...)` 唯一索引维持大小写唯一性，切换时登录查询与 slug 查询也必须同步改成同一语义。`normalized_name` 仍由服务层统一规范化后写入。

迁移基线位于 `backend/src/main/resources/db/postgresql/V1__portfolio_and_document_core.sql`，`application-dev.yaml` 已将 Flyway 扫描位置设为 `classpath:db/postgresql`。旧 MySQL 迁移文件留作历史资料，不在当前运行路径。

## Document / Blog 生命周期

1. 站内编辑或 Markdown Importer 生成 Markdown 与 `asset://<id>` 引用；原始文件格式不进入业务核心。解析所有引用并拒绝无法归档、未获使用授权或不属于本次保存请求的 Asset，不允许渲染器回退到第三方原图。
2. Service 校验每个引用的 Asset 已归档、处于 READY 且拥有使用权；在事务中创建不可变的 `document_version`，写入精确的版本 Asset 清单、标签显示快照和该版本的阅读时长，再以 `lock_version` 比较并更新 `document.current_version_id`。旧 `document_version` 及其关联行不得原地改写；READY Asset 的 `storage_key`、二进制对象和对外可见元数据不得覆盖，替换图片须创建新 Asset。
   - 已被公开版本使用的 Tag 全局 slug 不再改写；可调整全局显示名称，但旧版本继续显示自身的 `tag_name_snapshot`。筛选以稳定 Tag ID 或不可变 slug 为准，避免历史标签链接失效。
3. 公开博客只读取 `blog_post.published_version_id`。标题、摘要、正文、封面和标签都取自该版本；编辑后未重新发布时，读者仍看到旧版本。重新发布时服务层验证 slug、资源和权限，再原子切换已发布版本。
   - 重新发布前，服务层须确认目标版本确实属于 `blog_post.document_id`，且该版本是站长明确选择的待发布版本；仅凭外键存在不足以证明归属。
   - 保存新版本不得改变 `published_version_id` 或公开更新时间；下架后公开查询不可继续返回旧版本。历史版本正文与关联资源不可原地更新。
4. 公开媒体读取与导出必须从当前可见的 `published_version_id` 解析 `document_version_asset`，并逐次校验发布状态、Asset READY 状态及用途；仅知道自增媒体 ID 或在 Markdown 中写入 `asset://<id>` 不产生访问权。草稿预览仅站长可访问，缓存不得在下架后继续暴露资源。
5. RAG 只消费指定 DocumentVersion；Chunk/Embedding 是可重建派生数据。构建私有草稿索引不意味着访客可检索；公开 Agent 的每次检索须按发布版本指针或独立批准的知识用途与访问策略过滤，不能只按 `document.current_version_id` 或索引存在性放行。尚未定义非博客文档的公开知识用途，第二阶段启用 Agent 前必须先确定权限模型并以单独迁移落库。Embedding 模型、维度和 pgvector 扩展尚未验证，向量表和索引也留到第二阶段。
6. Markdown Exporter 从指定版本和 AssetResolver 生成结果；站长可导出自己的草稿和已发布版本。普通访客必须先登录且账号处于有效状态，文章已发布并按篇允许下载，才可导出其已发布版本；`allow_visitor_download` 单独不能授权。每次请求都重查身份、发布状态、下载许可及版本 Asset 权限。公开阅读仍可匿名。普通账号注册/登录的具体流程在博客模块启动前单独设计与验收。

## 旧数据到新模型的确定性映射

- 迁移时先暂停写入并重新盘点。现有 `article.id` 同时保留为新 `document.id` 与 `blog_post.id`；`article.source_type` 映射到 `document.origin_type`（0=站内创建，1=导入）。一篇旧文章只生成一个初始 `document_version`，其 `version_number=1`。旧 `article.version` 是乐观锁计数，不是历史正文版本号，映射到 `document.lock_version`，不得凭它伪造缺失的历史版本。
- `article.title/summary/body_markdown/reading_time_minutes` 进入初始 DocumentVersion；`article.slug/status/allow_visitor_download/published_at` 进入 BlogPost。已发布文章的 `published_version_id` 指向初始版本；草稿为空。所有文档的 `current_version_id` 指向初始版本。
- `article_tag` 转为初始版本的 `document_version_tag`，从迁移时 Tag 取显示名称与 slug 快照。`article_media` 转为初始版本的 `document_version_asset`；必须核对 Markdown 中每个 `asset://` 或旧站内媒体引用与关联清单一一对应，发现缺失、失效或非 READY 资源时阻止自动发布并记录修复项。
- `article_import_job.article_id` 映射为新 `document_id`，成功产生版本的任务才设置 `document_version_id`；旧 `source_type` 按明确枚举映射 `source_format`。保留原始时间戳并校验 UTC 语义，不推断未保存的原始文件或历史内容。
- 在临时 PostgreSQL 库执行迁移并核对每张表数量、旧文章到 Document/Blog/Version 的一对一映射、关联和登录哈希。显式导入旧 ID 后，逐表推进 Identity 序列至当前最大 ID；再用事务内新建测试记录确认不会碰撞。迁移脚本和验证报告通过审查后才允许切换开发配置。

## 切库验收门槛（原计划与当前进度）

以下是切库前制定的验收门槛。当前真实开发库的数据与接口切换已完成；旧文章及其资源记录为零，其非空迁移路径仍属于 T064 的未完成范围，不应将“本次无数据”误称为完整演练：

1. 对现有 MySQL 独立测试库做可恢复备份；短暂停止写入，不做双写。
2. 在 PostgreSQL 实际执行基线迁移，并通过结构测试：自增主键、数值状态、唯一索引、外键不级联、版本指针及索引。
3. 搬迁已有站长账号、资料、标签及任何届时新增的项目/媒体/文章；保留关联 ID 与密码哈希，导入后推进 Identity 序列。
4. 比对各表行数与关键关联，验证登录、公开资料、技术栈和 Knife4j 接口行为不变。当前只读盘点：账号 1、资料 1、标签 22，项目/文章/媒体均为 0；切库时必须重新盘点，不可依赖这次快照。
   对文档功能另做生命周期验收：发布 v1 → 编辑保存 v2 后访客仍看到 v1 → 显式重新发布后才看到 v2；检查标题、摘要、封面、标签、正文和下载权限一致，且禁止将别的 DocumentVersion 发布到此博客。
5. 通过后切换开发配置。若验证失败，保持 MySQL 预览不变；不得把半成品 PostgreSQL 连接当成可用服务。
