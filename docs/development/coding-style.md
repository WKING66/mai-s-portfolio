# 后端编码规范

本文规定后端代码组织、Java、POM、SQL 和相关配置的编码要求。功能测试同样遵循相关规则，存量治理限于授权范围。交付和验证见 [Git 工作流](git-workflow.md)。

## 强制执行方式

- 直接按本规范编写并定向整理任务涉及的代码。旧代码和 IDE 默认配置不改变本规范。
- 项目不使用自动源码格式化器，也不绑定自动格式门禁。Agent 不执行 Google Java Format/Spotless 等重排命令，不启用 IDE 保存时或提交时自动格式化，不擅自引入替代工具；未来采用工具必须先验证全部规则兼容并由维护者批准。
- 私人 IDE 设置不纳入 Git；使用编辑器的人应关闭会覆盖本规范的自动格式化。规范约束 Agent 的执行行为，不声称文档能强制控制所有个人插件。

## 不改变业务事实

纯排版或可读性整改保持 API 路径、字段与响应、数据库 Schema/Flyway、鉴权授权、Document 版本、事务与补偿、OSS 签名权限及 Bean 装配契约不变；不顺带升级或删减应用依赖、改变 Scope 和模块顺序。业务修复与构建治理按维护者授权范围实施，不能伪装成格式调整。

## Java 排版

- UTF-8、LF，基础缩进四个空格，不使用 Tab。mai-portfolio-backend/.gitattributes 固定 Java/POM 的 LF。长参数、注解或表达式在职责清晰的位置换行，续行缩进保持一致；不为了固定列宽拆坏字符串或表达式。
- if/else、for/while/do、switch、try/catch/finally 使用清晰换行和大括号，禁止把控制流程或方法体压成一行。多语句 Lambda 同样展开，长注解、参数、构造器和复杂 Stream 清晰换行，不机械压缩。
- Stream 管道必须展开：stream() 之后的每个中间操作和终结操作各占一行，包含 if 条件、方法实参和返回表达式中的管道。Lambda 有多条语句时展开代码块并正确缩进；禁止为了缩短文件把 filter/map/collect/toList 等挤在一行。
- import 统一排序，代码使用简单类名；只有真实同名冲突无法通过 import 消除时才保留必要的全限定名。核对导入、嵌套类型及静态调用，不能改变类型绑定。反射、配置、切点表达式中的类名字符串属于运行契约，不能作为源码类型引用删去包名。
- SQL、正则、文本块和长字符串首先保持实际值不变。跨行整理须核对字符串值和 SQL 参数绑定，不拆成无意义的碎片。
- 方法和构造器内不声明 class、record、enum 或接口；AST 遍历、资源状态和复杂处理回调使用独立具名类，不改写成大型 Lambda 继续堆叠逻辑。每次操作的可变状态显式按调用创建，不能放进共享 Bean。简单专用行为可用类级 private static 方法；仅记录日志等必要框架回调不做机械拆类，不能承载业务逻辑。
- 复杂方法只在职责明确且行为等价时局部拆分；不为了排版引入 Factory、Strategy、Registry 或万能工具类。

正确的简单方法也应展开：

```java
public boolean exists(Long documentId) {
    return documentMapper.exists(documentId);
}
```

## 数据类字段排版

所有生产数据类统一执行，包括 DTO、VO、DO、跨模块传输对象、配置数据类及嵌套 record；不因使用 class 或 record 而采用两种字段排版。

- 字段声明和注解不得写在同一行，每个注解单独一行，与所属字段保持相同缩进。
- 每个字段单独声明，相邻字段之间保留一个空行；record 组件按字段处理，包括没有注解的组件。
- 保留字段顺序、注解参数、泛型、默认值及既有业务方法；不为了排版把 record 改成普通 Bean。

```java
public record ExampleRequest(
        @NotNull
        @Positive
        Long version,

        @Size(max = MAX_TITLE_LENGTH)
        String title,

        boolean enabled) {}
```

上述排版是强制标准，包括未加注解的字段和单字段 record。不得把多个字段压回同一行，也不得用切换为普通 Bean 来规避 record 排版。

## 依赖与变量命名

- 所有 Service/Mapper 类型的字段、构造器参数和局部引用使用明确的 xxxService/xxxMapper：blogService、documentMapper、userAccountMapper。禁止用 blogs、versions、mapper 等集合式或泛称表示依赖。
- 实体使用单数，集合使用对应复数：documentVersion 与 documentVersions。Converter 与业务 Service、数据 Mapper 分清职责。
- SDK 与基础设施按实际类型和用途命名，例如 ossClient、redissonClient、redissonLock、saTokenSession、redisTemplate；只有实际使用 Quartz 或 XXL-Job 时才使用 quartzScheduler、xxlJobExecutor。
- 已封装的对象按抽象职责命名，例如 objectStorage；不能为了规范把存储抽象叫 ossClient。client、manager、handler、obj、data、temp 等只在极小且含义明确的上下文使用。
- 重命名同时核对构造器、Lombok 生成注入、Qualifier/Resource、按名称装配、反射及测试引用。公开 DTO/VO 字段、JSON 属性、Bean 名称和第三方 API 名称不能作为普通变量随意重命名。

## 对象转换与输入校验

- 每个业务 service 模块的转换接口放在自身 convert 包，使用 MapStruct 的 org.mapstruct.Mapper；数据库 Mapper 继续放在 mapper 包，使用 org.apache.ibatis.annotations.Mapper，不混用两者职责。
- 无状态、无外部依赖的转换器使用静态 MAPPER = Mappers.getMapper(...) 和 to(...) 重载，保留 record，漏映射在编译期报错。转换器只装配字段和编码，不查询数据库，不决定权限、发布状态或版本选择。
- 同一业务事实在 Request、DTO、DO、VO 与前端中优先采用一致字段名、类型和语义，先确定接口契约再开发，避免每层另起名字。已发布字段不为减少映射注解而频繁重命名；内部 Java 字段对齐时明确保留旧 SQL 列名，不修改历史迁移或增加新旧双字段。
- Convert 优先处理已有对象之间的同名字段转换，不逐字段枚举同名 @Mapping，不把全部字段拆成标量参数后包一层生成构造器，也不新增仅用于缩短 Convert 签名的镜像 DTO。
- 分页结果、导入默认值、版本号/编辑人/时点等生命周期事实由调用业务创建或确定，不伪装成通用字段转换。已有对象之间的正文、属性等重复字段继续使用自动映射，不因精简 Convert 而搬成 Service 中的逐项赋值。业务聚合确需多个来源时，保留清楚且必要的映射。
- 真实语义差异（账号 ID/文档 ID、内容版本/锁版本）不能强行统一名称；稳定 API 与存储边界的必要别名只维护一处。多来源同名属性需要明确正确来源，不能为了删注解而改变选择。
- 枚举存储编码集中复用既有类型规则，不使用 ordinal，不为每个字段复制 java(...) 字符串表达式；不通过忽略全部未映射字段来隐藏遗漏。新增普通同名字段应由 MapStruct 自动映射，无须再修改转换方法。
- HTTP 请求的必填、长度、范围和格式约束使用 jakarta.validation，由 DTO 注解及入口的 @Valid/@Validated 触发；有真实动作差异时使用校验分组，不在 Service 重复实现同一套字段格式判断。
- 权限、唯一性、版本 CAS、发布完整性、资源归属及动态配置限制属于业务规则，保留在相应业务边界。业务拒绝和参数校验异常不得混用。
- Hutool 用于语义等价的空集合、默认值等冗余操作；不为替换简单的 == null 而增加绕行，不改变 null/空串/空白、Unicode、路径或权限判断的业务含义。

## 中文业务步骤与 JavaDoc

入口看链路，子方法看规则，关键实现看原因。复杂 Service、多步骤事务、认证授权及 Document/Asset 等资源生命周期必须按这三层写中文业务注释。

### 业务入口与编排

按真实执行顺序使用中文编号步骤（如 `1. 读取……`、`2. 校验……`）。标明读取或锁定、业务判断、写入和状态变更、结果处理等实际步骤。依赖顺序有业务意义时写出原因，详细规则留在对应实现。

```java
@Transactional
public void publishBlog(Long blogId) {
    // 1. 读取博客及本次发布所需的状态
    Blog blog = loadPublishContext(blogId);

    // 2. 校验草稿、Slug 和资源是否满足发布条件
    validatePublishConditions(blog);

    // 3. 将工作草稿提升为正式正文
    promoteDraftToContent(blog);

    // 4. 更新博客公开状态
    updatePublishStatus(blog);
}
```

示例用于展示注释结构，实际发布顺序以当前实现为准。

### 承担具体规则的方法

在规则所在的方法解释触发条件、已确认的业务依据、允许变化和必须保持的状态、拒绝后的用户可见结果与可行的下一步。业务拒绝必须能追溯到明确的业务规则。依据可用具体业务要求或验收约束表达，避免虚构需求编号。事务、锁、跨系统调用和补偿由实际执行它们的方法说明。

### 关键判断与失败路径

在非显然的状态转换、跨槽位合并、排序优先级、去重、资源生命周期、锁协议、幂等及补偿附近写清原因和失败后果。优先级、合并和去重在代码中显式表达。例如同一资源 key 同时出现在草稿和正式正文时显式选择草稿，避免旧正文的就绪状态覆盖草稿中的失败状态。草稿移除但正式正文仍引用的资源继续保留，以便撤回或复用。

涉及数据库、OSS、Redis、缓存、上传或凭据失效时，说明实际事务边界、锁的持有与释放条件、外部副作用及失败后的真实补偿。数据库回滚无法撤销 OSS 写入。存在补偿时写明执行方与触发条件，注释与现有实现一致。

重要公共方法使用 JavaDoc 说明职责、关键参数约束、返回语义和主要失败边界。注释使用草稿、正式正文、发布、下架等当前业务术语，实现改变时同步更新。避免把测试编号、空泛的「幂等处理」或显而易见的赋值当作业务解释。

### 结构与审核

方法按真实职责与内聚性拆分。保留一眼能读懂的短步骤，复杂规则放入承担该规则的方法。避免巨型编排方法、只为凑步骤而提取的转发方法，以及跨方法重复描述同一业务事实。简单委托和 Getter/Setter 无需额外注释，不按固定比例或行数评判。

审核时沿入口到实现核对步骤和职责，检查关键决策、状态变化、拒绝与恢复路径是否有足够的业务解释，并核对注释与代码一致。缺少必要注释须在正式交付前修复。

## 业务优先与职责收敛

- 以已确认的业务问题决定实现，技术方案负责实现业务，不自行引入高并发、强一致或假设性扩展来改变需求。
- 保持职责内聚：在已有服务中完成属于同一业务的逻辑；只有明确的独立职责、变化原因或复用需要才新增类或接口。新增一层应说明它实际解决的问题，单纯转发不构成独立职责。
- 同一规则有一个明确来源。入口负责请求认证及授权，Service 负责业务状态、资源归属和业务写入；不在每个调用层重复登录、角色或账号有效性检查。
- 共享上下文保存当前会话用户必要的脱敏信息，调用方直接读取，不再经过身份 Service 或代理接口。完整数据库实体、密码摘要等不得进入共享上下文；需要完整账号数据的业务写操作自行读取。
- 简化时核对事务、异常、权限与失败补偿语义；减少类或方法数量本身不是目标，也不能据此省略业务必需的检查。

## 业务模块目录

- 一个业务模块保留一套 Controller、Service 接口与 Impl、Mapper。配置、实体、枚举、常量和功能组件放入对应职责包。
- 模块内部禁止按子业务再嵌套一套三层架构。并入 System 的标签类直接使用 `system/service`、`system/mapper` 等既有职责目录，避免 `system/tag/service` 等嵌套。
- 确有独立业务边界时拆为同级 Maven 业务模块。

## 常量、异常与局部结构

- 可复用业务判断留在现有业务层，复用同一来源，不放入 Controller、DTO、Mapper 或通用工具类。
- 业务限制、状态码、资源用途及配置值复用已有常量、枚举和 Properties。语义明确的局部索引或计数初值不机械抽成常量；新增常量须有真实业务含义。
- 异常应体现当前边界与上下文，不把业务拒绝转换为校验异常，不吞异常或以默认值掩盖失败。若修复会改变既有异常契约，另行提交业务修复。
- 日志符合现有规范，不输出密码、凭据、令牌、带签名的完整 URL；不重复记录同一异常。必要日志调整先判断实际影响。
- 简化局部嵌套或提取方法时保留异常抛出顺序、短路判断、锁/事务作用域、返回顺序与外部调用次数，不借本轮进行架构重构。

## 分页、关联查询与热点读取

- 所有分页请求复用 common.PageRequest，page/size 的默认值和校验仅定义一处。领域请求可继承并增加筛选字段，不复制分页字段；需要不同默认条数时显式使用 sizeOrDefault，不修改查询参数形状。
- 所有分页响应基于 PageVO<T>；没有额外字段就直接使用，多个领域共有的额外字段（例如 view）复用同一扩展，不为每个接口创建一套分页对象。
- 同一读取阶段涉及不超过三张表时采用有索引支持的 JOIN；整条业务链涉及更多表时拆成多个不超过三表的关联阶段，批量查询后按 ID 在内存装配。不得用循环逐条查询代替批量关联。
- 一对多关联分别批量读取，避免把长正文与图片、附件、标签一起 JOIN 造成重复行或分页计数错误；查询优化不得改变草稿/正文选择、资源归属或公开权限。
- 多条关联写入先在内存组装，再复用 MyBatis-Plus 批处理，保留原事务与失败回滚；空集合不执行批写。
- 对已明确的读多写少热点使用有失效策略的缓存，说明缓存范围、过期时间和写后失效。不得把权限或草稿混入公开缓存，也不能让签名 URL 的缓存超过其有效期；不为假设性热点引入额外基础设施。

## 数据库分类编码

- 所有自有业务表的有限类别、用途和状态列统一使用 SMALLINT；枚举显式声明稳定 code，不使用 ordinal 或在不同表中另建同一类别的字符串编码。
- API 对外名称与存储编码分开：既有 JSON 名称保持稳定，必要转换留在模块 Convert 或原枚举中，避免数据库改类型迫使前端同步改字段。
- 已执行迁移不得修改；通过新增迁移转换既有值、保留数据和必要索引。未知值明确停止迁移，不默认归入某个业务类别。
- MIME 等开放文本和第三方框架自行管理的元数据不属于有限业务分类，不机械改为 SMALLINT。

## POM、XML、YAML 与 SQL

- POM/XML 四空格缩进，dependencies、dependencyManagement、plugins、executions、profiles、properties 等结构按层级换行。叶子文本可在同一行，禁止多个依赖元素挤在一行。
- 保留依赖、插件、模块、属性和 executions 的现有顺序，不因排版改变 Maven 语义；纯排版后用 XML 解析核对结构和文本，构建配置改动明确说明意图。
- 运行时 YAML、Mapper XML 和 SQL 可读性整改保持解析值、占位符、参数和顺序；不重写历史 Flyway SQL。注解中的 SQL 字符串按实际值核对。
- 普通单表 CRUD 使用 MyBatis-Plus。较长 SQL、多字段更新、JOIN、子查询、聚合及动态 SQL 统一写入所属 service 模块 `src/main/resources/mapper/<Mapper名>.xml`；Mapper 接口保留签名和 @Param。仅简单、短小的单表语句或锁函数调用可用 SQL 注解，不用字符串拼接或文本块把复杂 SQL 塞回注解。迁移时逐项核对 namespace、statement id、参数绑定、结果映射及 XML 转义，保持原业务和事务语义。
- 所有自有 POM 纳入检查，包括不继承根 POM 的 BOM；不因独立父子关系遗漏文件。

## 代码自检

- 按本次差异核对排版、命名、转换、职责边界和中文业务注释，检查关键成功及失败路径。
- 可读性整改核对字段顺序、注解参数、默认值、SQL 绑定、事务、权限及外部副作用的行为等价性。POM/XML 核对结构和文本，保留必要的编译器和注解处理器配置。
- 仅整理已授权范围内的受影响代码。复用已确认的业务与编码决策，避免重复格式迁移。
