# Git 协作与分级验证规范

## 任务基线与提交

1. 按 [AGENTS.md](../../AGENTS.md) 检查自己的 Worktree、分支、基线与待保留的工作。获取最新 `origin/dev`，为新的独立任务从该基线创建任务分支，例如 `codex/<task>`。使用现有 Worktree，只有工作区可安全切换时才切换。已有 WIP、分支或 PR 先保留，继续已有任务时沿用其分支。
2. 从实际需求确定验收范围和验证等级。按[文件收录](#文件收录)检查和暂存差异。已提交的依赖声明及其锁文件保持一致，说明新增或升级依赖的用途和部署影响。
3. Commit 使用 Conventional Commits 和准确的 scope。开发中可保留多个中间提交。验证针对要交付的 HEAD 与受影响范围。审查期间正常追加本任务修订。
4. 任务 PR 以 `dev` 为目标，由维护者审核后使用 **Squash and Merge**。禁止直接向 `dev` 或 `main` 提交任务实现。历史 `backend` 和 `frontend` 分支保留到经批准的迁移，日常任务从 `origin/dev` 开始。

前后端通过 `dev` 取得已集成的代码与 API/OpenAPI 契约，未合并的实现不作为已集成基线。遇到接口不兼容或数据库迁移冲突，先确定解决方案再交付。

## PR 范围与状态

- 一个完整、可独立验收的交付目标默认对应一个 PR。判断拆分时看是否有独立业务价值、能否独立验证和合并，以及是否确实降低审核成本。行数仅作参考。规模大时提供核心入口、阅读顺序及验证证据。
- 确需多个 PR 时，创建前向维护者说明拆分理由、依赖关系和合入顺序，取得批准。默认不创建 Stacked PR。已批准的依赖 PR 在其实际前置基线上通过 CI，前置合入后由 Agent 更新目标到 `dev`，检查最终差异并重跑 CI。需要重写历史时先取得授权。
- 正式交付使用 Ready for review。实现未完成或存在阻碍正式审核的明确问题时，只有维护者同意提前公开才创建 Draft，并写明阻塞及转正式的条件。已完成实现和自测的视觉、业务验收，以及正式 PR 的审核修订，在原 PR 标注待验收项即可。

## 交付前独立审核

- 每次创建 PR 或推送审核修订前，必须使用 `open-code-review-delegate` 委派独立子 Agent。首次审核完整任务差异，修订时审核相对上一轮的增量及直接受影响的依赖。已审且未变更的结论可复用。纯文档按 V0 核对规则、引用、冲突与范围。
- 子 Agent 重点核对业务正确性、职责和架构、必要业务注释、失败路径、事务和资源边界，以及回归风险。后端注释按[中文业务步骤与 JavaDoc](coding-style.md#中文业务步骤与-javadoc)审核。CI 承担可自动化的客观检查。
- 发现问题先汇报，由开发 Agent 修复并验证，再交独立子 Agent 复审相关差异。通过后才创建 PR 或推送审核修订。

## 人工审核与修订

人工审核以最新 HEAD 相对目标分支的最终代码差异和验收结果为主。复审另提供从上一轮已审版本起的新增差异。维护者可以查看提交历史。已有审核结论适用于未变更且未受影响的代码。

审核未通过时，在原 PR 分支内修复当前验收范围的问题，执行关联验证和独立复审，更新正文及待验收事项，再交付维护者。可用简短评论保留每轮反馈与处理结果。正常追加修订，合并时统一 squash。

PR 正文反映当前交付状态，可用以下结构：

- **本次交付**写明实现、验收范围和当前状态。
- **关键实现**给出主要入口、类或方法和建议阅读顺序，说明关键设计取舍、依赖及其必要性、API、Schema 或配置变化。
- **验证结果**写明验证等级、检查结果及适用的代码版本、未覆盖内容和风险。
- **最新审核修订**写明本轮解决的问题、未采纳反馈及理由、待确认事项和应复查的功能。

交付消息以 PR 链接和需要维护者确认的内容为主。审核材料、日志和截图只保留必要的证据。

## 合并后准备与存量迁移

- 确认任务合入后，由 Agent 获取最新 `origin/dev`，在自己的可安全切换的 Worktree 中准备下一任务的干净基线。工作区目录长期保留，切换任务分支无需重建 Worktree。
- 清理任务分支前确认 PR 已合并，成果确实进入 `dev`（Squash 合并需核对合并提交或最终差异），无须保留的独有修改，且没有活动任务、依赖 PR 或 Worktree 仍在使用该分支。满足这些条件后，按授权范围清理本地和远程任务分支。
- 迁移现有长期分支、WIP 和 Stacked PR 前，逐项盘点基线、所有者、独有提交、WIP/stash、工作区占用和依赖关系。先列出处理顺序和安全迁移建议，由维护者批准，再逐项处理。保留未合并成果与已有审查记录，禁止批量删除或重写。

## 发布与保护

- 维护者决定发布时固定 `dev` 候选提交，暂停向候选引入新功能。对该版本执行发布构建、必要安全检查和前后端关键业务真实验收。
- `dev → main` 发布 PR 记录候选版本、验收范围和未验证内容。维护者最终批准后使用 **Merge Commit**。发布后由获授权的集成负责人核对并同步 `dev` 与最新 `main`，只能安全快进时快进，有分叉先协调。发布失败按任务 PR 流程修复并重新验收。
- `main` 和 `dev` 应保护免受强推和删除，要求 PR、审核及实际已启用的必需检查。`main` 的保护配置须兼容发布 Merge Commit。启用 required checks 前确认检查实际存在。保护设置与自动合并权限按 [AGENTS.md](../../AGENTS.md) 审批，此处描述工程要求。

## 最小充分验证

按行为和影响判断风险。混合变更覆盖最高实际风险，验证范围围绕受影响的成功、失败路径及数据一致性。配置值影响运行行为时按实际风险定级，配置说明可按 V0。验证等级不能替代业务审批。

| 等级 | 适用范围 | 最小充分验证 |
| --- | --- | --- |
| V0 | 纯文档、纯注释、Git/Commit/PR 操作、行为等价的排版 | `git diff --check`，按需检查内容、Markdown、引用、格式或 XML 结构。跳过应用构建、应用测试和端到端测试 |
| V1 | 简单、低风险局部修改 | 直接关联的轻量检查 |
| V2 | 普通 Controller/Service、常规 Bug、局部接口和一般功能 | 受影响模块的功能测试及必要编译 |
| V3 | 认证授权、权限边界、Schema/迁移、资源控制、破坏性 API、核心公共架构及关键跨模块链路 | 充分的定向回归及必要的真实集成。影响广时可扩大到全量，覆盖关键拒绝路径和数据一致性 |

- 本地运行适用的关联测试和已有 lint，CI 承担统一门禁。已通过且未受影响的检查可复用，注明适用版本和范围。失败先定位根因并复跑关联检查。缺少工具或环境时报告未验证范围，不降断言或静默跳过。
- 检查命令以各模块实际配置为准。Nuxt 使用 `package.json` 脚本，Python 使用项目配置的 Ruff、Pyright 和 pytest，Java 使用关联 Maven 模块及适用的编译检查。
- 前端视觉、交互和响应式变更按验收标准自检。有真实浏览器条件时运行关键流程，提供必要截图、复现步骤或验收说明。标注未验证的视觉和交互。
- 测试替身的结果与真实数据库、Redis、OSS 和浏览器验证分别记录。真实写入使用隔离库、独立 Redis 命名空间及已授权的 OSS 对象。默认本机前端为 3000、后端为 9333。确认依赖和数据隔离，保留维护者及其他 Agent 正在运行的服务。
- 现有 PR 门禁由 `.github/workflows/pr-gate.yml` 定义。检查具体运行结果后再确认覆盖范围。必需检查应始终触发并在内部按差异选择工作，避免路径过滤导致长期 Pending。

## 文件收录

- 精确暂存任务内容。提交生产代码、有效功能测试与必要支撑、项目文档和安全配置模板。凭据、私有配置、无关排版、测试产物和用户未提交的工作留在提交外。
- 对外启动、使用、必要设计和数据库说明放在 `resources/`。内部交接、阶段报告、截图及临时工具留在 `private/`。维护者指定的共同工程规范可纳入 Git，运行时 SQL 保持唯一来源。
- 联调、浏览器、性能、Windows shell 与辅助脚本用完清理。功能完成后撤出演示入口、组件和 URL，保留实际覆盖业务的测试。
