# Git 协作与分级验证规范

Agent 专注开发，dev 负责集成，main 负责稳定发布；日常最小充分验证，发布阶段集中验收。

本文是共同工程流程的唯一完整来源，根目录 [AGENTS.md](../../AGENTS.md) 只保留执行约束。共同规范由后端 Agent 维护，前端 Agent 不同时编辑，仅提供建议。本规范替代此前普通任务直接向 main 提 PR、每项任务必须新建分支、合并后删除所有开发分支的旧规定。

## 四分支与独立工作区

| 分支 | 职责 | 起点与 PR 方向 |
| --- | --- | --- |
| main | 稳定版本、发布基线 | 仅接收审核通过的 dev → main 发布 PR |
| dev | 统一集成、联调测试 | 首次从最新 origin/main 建立；接收已完成的开发 PR |
| backend | 后端 Agent 长期开发 | 首次从最新 dev 建立；日常 backend → dev |
| frontend | 前端 Agent 长期开发 | 首次从最新 dev 建立；日常 frontend → dev |

- 前后端使用各自独立 Worktree，不共享可写目录，不在另一 Agent 的分支开发，不重复创建已有工作区。
- 开始任务检查 Git 状态、当前分支和基线 SHA，保留已有修改、stash 和未合并成果；未知 WIP 不切换、覆盖或清理，正在使用的 Worktree 不删除。
- dev 缺失时由指定集成负责人从最新 origin/main 初始化并推送；这是首次建立基线，不是允许日常直接向 dev 提交功能。
- backend/frontend 是长期分支，合并后不删除；每个长期工作分支通常只保留一个待合并 PR。待审核期间修订当前 PR，不把下一项未完成任务混入它。
- 默认只保留 main、dev、backend、frontend 四个长期分支。确需并行且不能混入未完成代码时，可从自己的长期分支建立短期任务分支，例如 feat/backend/<task>、fix/backend/<task>、refactor/backend/<task>、chore/<task>，前端对应使用 frontend scope。核对 PR 完整变更范围，目标仍为 dev；集成并同步长期分支后删除无用短期分支的本地与远程引用。
- 不默认建立多级父分支。大型功能确需多 PR 集成时，临时 epic 父分支须先获维护者批准，完成后删除。
- 工作流迁移先保留现有分支与 WIP；已有 PR 检查范围后可改目标为 dev，尚无 PR 的成果由所属 Agent 安全迁移或以短期分支提交。不得为切换流程 reset、擅自 rebase、丢弃代码或强制推送。
- 若 backend/frontend 名称被旧的同名前缀分支占用，先核对独有成果与归属；有效工作完成迁移后删除已废弃引用，不把旧分支改名当作长期保留理由，也不清理仍在使用的工作区。
- 未经授权，不直接向 dev/main 提交或推送功能，不自行合并 PR，不删除或强制改写公共长期分支。

## 日常开发、Commit 与 PR

1. 每次新任务开始前，在自己的 Worktree 检查分支和未提交修改，保护 WIP；必须执行 git fetch origin，将最新 origin/dev 快进到自己的 backend/frontend 并推送开发分支。同步成功后才能开始新任务，不为普通读文件或每个 Commit 反复 fetch。
2. 实现已授权功能，执行与风险相称的最小充分验证，并检查实际 Diff。
3. 精确暂存本任务文件，使用 Conventional Commits，例如 feat(backend-document): support version export、fix(backend-auth): correct session validation、refactor(frontend-toc): simplify scroll tracking。
4. 提交并正常推送自己的分支，创建指向 dev 的 PR。一个 Commit 有明确职责；不无检查地 git add .，不混入无关格式化、重构、他人 WIP、凭据、本地配置或测试产物。
5. PR 简述本次功能、修改范围、验证等级及结果、接口/Schema 变化和已知风险。开发 Agent 自查；独立 Review Agent 可补充审查；CI 承担客观门禁；由获授权的维护者审核合并。
6. 审核修订留在当前分支，复验受影响范围。不得为美化历史反复重写公开提交。未授权自动合并，也不通过保护设置绕过审核。

长期分支之间统一使用 **Merge Commit**：backend → dev、frontend → dev、dev → main 均禁止 Squash and Merge，也不使用 Rebase and Merge。此方式保留祖先关系，使开发分支可直接快进到集成结果，避免反复出现已经合并的代码。

每次新任务开始前，以及确认本轮 PR 提交已进入 dev 后，对应 Agent 必须在自己的干净工作区执行以下同步。纯同步属于 V0，不触发 Maven、Nuxt 或端到端测试。后端示例：

```text
git status --short --branch
git fetch origin
git switch backend
git merge --ff-only origin/dev
git push origin backend
```

前端将示例中的 backend 换成 frontend。已有进行中的任务、未合并 PR 或 WIP，先保护进度和核对状态，不照抄切换命令或为了同步丢弃成果；只有确认本轮提交已进入 dev 后才开始下一轮同步。无法快进时检查未合并提交、未完成任务和分叉原因，选择保留成果的合并/协调方案，不强制 reset、强推或擅自重写历史。

## 集成与发布

- dev 是前后端已集成代码的共同来源，只接收达到完成标准的功能。跨端功能先按正常 PR/审核流程在 dev 确认 OpenAPI 契约，双方基于确认的契约分别开发；另一 Agent 的未合并代码不能假设已在 dev。依赖通过明确接口交接或提前合入可独立验收的契约变更解决。接口不兼容或数据库迁移冲突先明确方案再合并，不以覆盖一方消除冲突。
- 维护者决定发布时固定待发布 dev Commit，暂停向该候选引入新功能；针对该版本执行发布构建、必要安全检查与前后端关键业务真实验收。
- 验收通过后创建或完成 dev → main PR，列明候选版本、覆盖范围和未验证内容，由维护者最终确认并使用 Merge Commit 合并。
- 发布完成后，由获授权的集成负责人使 dev 快进到最新 main；前后端 Agent 再同步最新 dev。若存在新的未合并提交或无法快进，先核对，不强制覆盖。
- 发布失败在相应开发分支修复，按正常 PR 流程重新集成并复验，不直接向 dev/main 补功能。
- 普通任务不重复基线迁移、历史审计或全链路验收。后端恢复任务前阅读当前实现、核对未完成事项；已完成或失效的任务如实说明，不擅自启动新的大型功能。

后端编码必须执行 [后端编码规范](coding-style.md)：开发前完整阅读，提交前逐项自检与 Review；不依赖自动源码格式化器或自动重排门禁，风格以该规范为准。纯排版仍按 V0 验证。

## Minimum Sufficient Verification

先判断行为及影响范围，再选择等级；风险不按文件数量划分。一个任务含多类变更时覆盖最高实际风险，验证仍围绕受影响范围。

| 等级 | 适用范围 | 最小充分验证 |
| --- | --- | --- |
| V0 | Markdown、README、纯注释/说明、Git/Commit/PR 操作、未改变行为的配置说明 | git diff --check 与必要内容、引用、格式检查；不运行应用测试、Maven 全量测试、Nuxt 构建或端到端测试 |
| V1 | 简单、低风险局部修改 | 仅直接关联的轻量检查，不默认完整项目构建 |
| V2 | 普通 Controller/Service、常规 Bug、局部接口及一般业务功能 | 受影响模块的功能测试及必要编译；通过后停止，不自动扩大全项目回归 |
| V3 | 认证/授权、权限边界、Schema/迁移、资源控制、破坏性 API、核心公共架构、关键跨模块链路 | 按风险执行充分的定向回归与必要真实集成；影响广时允许全量测试，不省略关键拒绝路径或数据一致性检查 |

配置说明可为 V0；实际配置值、运行行为或权限变化须按影响重新定级。等级不能替代业务审批。

### 执行约束

1. 全量测试不是默认收尾，创建 PR 不触发重复应用测试；改前端不运行无关后端检查，改后端不默认运行全部浏览器测试。
2. 先明确关联模块、风险和成功/失败路径，再选检查；不为本轮重建大型测试框架。
3. 失败先定位根因，复跑关联测试；只有后续变更或未解决影响证明有必要时才扩大范围。
4. 已通过且未受影响的检查不重复执行；复用结果须确认代码、依赖、配置和环境仍适用，说明对应版本与范围。
5. 不为通过错误测试而修改无关业务、降低断言或静默跳过。无法验证时明确报告，不冒充通过。
6. Mock 不能称为真实数据库、Redis、OSS 或浏览器联调；真实写入使用隔离库、独立 Redis 命名空间及授权 OSS 测试对象，不动维护者现有数据。
7. 默认联调端口前端 3000、后端 9333；端口不能证明数据隔离。不强行结束另一 Agent 或维护者的服务。
8. 测试通过只是最低条件；还须检查业务事实来源、职责边界、重复规则、失败路径、配置/异常/日志与实际扩展点。明显结构问题未解决不得宣布完成。

### 本地与 CI 门禁

本地侧重快速反馈，CI 承担已启用的统一门禁。非关键任务不自行重复耗时检查；尚无 CI 覆盖的必要验证不能声称已由 CI 完成。

前端现有命令为 npm run typecheck、npm test（Vitest）、npm run build；定向单测可用 npm run test -- app/test/<关联文件>.test.ts。后端选择关联 Maven 模块、测试及必要编译，不固定运行全量 verify。它们不是每项任务的必跑清单；当前没有项目 lint 脚本或 Playwright 依赖，不写成已启用门禁。

以下为后续 CI 配置方案，本轮不新增工作流或测试框架，不能将建议检查称为已启用：

| 稳定门禁 Job | PR 目标 | 检查范围 |
| --- | --- | --- |
| pr-gate | dev | 始终启动；内部判断改动范围与风险，V0 仅检查 Diff/内容，前端或后端执行关联检查，跨端变更覆盖双方；必要静态/敏感信息检查 |
| release-gate | main | 发布构建、关键跨端真实验收与安全检查，关联固定候选 Commit；缺少真实依赖须明确失败或待人工验收，不能用 Mock 代替 |

不要通过路径过滤完全跳过必需检查所在的 Workflow，避免检查长期 Pending。保留稳定运行的门禁 Job，由内部步骤按需执行；无关联应用变化应说明原因后成功结束，不隐藏应执行检查的失败。

## 分支保护配置要求

下面是待配置并核实的要求；本文不表示 GitHub Rulesets 或 CI 已经配置。启用 required checks 前先确认稳定门禁实际存在，避免无法满足的 Pending 检查。

| 分支 | 保护要求 |
| --- | --- |
| main | 禁止强推和删除；必须 PR、发布门禁通过、维护者最终确认；正常发布来自 dev |
| dev | 禁止强推和删除；必须 PR、轻量门禁通过、审核后合并 |
| backend/frontend | 允许所属 Agent 正常提交与推送；不擅自删除、强推或跨 Agent 操作 |

不能为允许 Merge Commit 同时启用要求线性历史的规则；长期分支 PR 选择 Merge Commit，禁止 squash/rebase。自动合并仍须维护者另行授权。仓库已有管理员权限也不等于获准改变保护或审批策略；无权限时提供配置内容，不宣称已完成。

## Agent 职责与审批

后端 Agent 负责 Spring Boot、PostgreSQL/迁移、Redis、认证/授权/安全、Blog/Document/Asset、OSS 和后端 API/OpenAPI；前端 Agent 负责 Nuxt 页面、组件、交互、渲染与性能。

重要接口变化先明确契约。需要另一端配合时提供接口变化、所需修改与简短交接，不代改对方业务代码。共同规范只由后端 Agent 修改。

阅读代码、实现已授权功能、必要局部重构、分级验证、修复自身问题、Commit 和 PR 可自主执行；以下事项须先获明确批准：

- 重要架构调整、数据库破坏性变更。
- 认证/权限业务语义变化、破坏性 API 修改。
- 跨越前端职责的修改，尤其大范围修改。
- 合并 dev/main；强推、重写公共历史或删除长期分支。
- 变更 GitHub 保护/审批规则或启用自动合并。

当前优先博客与统一 Document 生命周期；RAG/知识库属于第二阶段。实现先识别稳定业务、已明确变化点、职责层与可复用逻辑，不为当前测试硬编码，也不为假设性未来需求堆砌抽象。

## 文件收录与日常交付

- 仅提交功能代码、功能单元测试与必要测试支撑、关键项目文档及安全配置模板；不能因放进 src/test 或 app/test 就提交本地工具。
- resources/ 收录对外启动、使用、必要设计和数据库说明。Agent/审核/交接/阶段报告、截图保存在 private/，不入 Git；运行时 SQL 保持唯一来源。
- 本地前后端联调、浏览器、性能、Windows shell 和辅助开发脚本不提交，用完及时清理。演示组件完成使命后删除，正式功能完成后不保留演示 URL；保留真正的功能测试。
- 维护者明确指定的共享规范 AGENTS.md、docs/development/git-workflow.md、docs/development/coding-style.md 纳入 Git，作为上述资料分类的特定例外；其他内部材料仍留 private/。旧 private/development/git-workflow.md 不再保留另一套规范，统一引用本文。切换 Worktree 后确认根规范存在再开发。
- 日常只报告完成内容、PR、验证等级及结果、接口变化和关键风险/阻塞；不生成不必要的长篇开发、审计或测试报告。
