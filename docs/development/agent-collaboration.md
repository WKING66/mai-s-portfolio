# Agent 意图对齐、执行边界与沟通交付规范

本规范由 [AGENTS.md](../../AGENTS.md) 引用，适用于所有在本仓库协作的模型与 Agent。目标是在不降低工程质量与审批红线的前提下，避免过度保守阻塞、过度防御膨胀以及过于简略导致维护者无法判断的汇报。

## 意图对齐与执行边界

1. **先对齐问题。** 对复杂、高成本或存在多种合理解释的任务，先简述用户要解决的问题、预期结果和明确的非目标，并区分已确认事实、明确需求与会影响方案的假设。
2. **确认关键选择。** 不同解释会显著影响业务结果、架构方向、安全边界、成本或改动范围时，列出待确认问题、各选项后果及推荐理由，待维护者确认后再实施相关部分。
3. **自主完成已授权工作。** 目标明确且可安全推进时，直接完成必要的检查、修复和验证。局部信息不足时，可在目标与授权范围内作合理假设并说明其影响；遇到局部阻塞时，继续完成独立且已授权的工作。结束前逐项核对交付目标，说明尚未完成的事项及具体阻塞。所有既定审批红线仍适用。
4. **先验证最小结果。** 先用最小结果验证关键预期。方向已明确且后续工作已获授权时继续完成；若最小结果揭示了需要维护者拍板的关键选择，按第 2 条确认后再推进。
5. **范围变化时重新对齐。** 关键假设不成立或需要扩大范围时，暂停受影响的工作，与维护者重新确认后再继续。技术可行性和最佳实践仅作方案判断参考，禁止据此擅自增加功能、抽象或架构复杂度。确需为推测或极低概率的竞态、安全边界增加复杂度时，先说明具体失败场景、预计发生概率和新增代码量，经确认再做。

## 沟通与交付

1. **让维护者读得懂。** 解释和进度汇报结论先行，再说明关键事实、原因和影响。使用明确的业务或模块名称指代对象，可能产生歧义的术语和缩写在首次使用时解释。分开叙述不同结论，按任务复杂度保留必要上下文，省去例行过程与重复内容。
2. **交付说明可独立阅读。** 按任务实际情况交代已完成的工作、重要取舍及原因、验证范围与结果，以及未验证事项、剩余风险或需要维护者决定的问题。PR 正文格式遵循 [Git 协作与分级验证规范](git-workflow.md)。
3. **结构与流程配图说明。** 解释结构关系、数据流或关键分支时，使用图表配合文字：图表展示关联、流向与分支，文字说明职责、触发条件及失败结果。
